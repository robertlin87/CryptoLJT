## 代码排查：全平后残留挂单清理的时间语义（未改代码）

- 用户观察：VPS 15:54:44 重启后，15:55:22 打印「🧹 全平後殘留掛單已清理 BSBUSDT（1 個 reduce-only）」，但那笔全平是更早的事，怀疑程序重连后重读历史消息。
- **结论：该日志与 TG 消息无关**。`execution/watchdog.py:28-53` 每 30s 全量对账（`fetch_all_positions` + `fetch_open_orders`），判定只有「symbol 无持仓 + 有 reduce-only 挂单 → 撤单」，完全不看消息、不看时间；日志文案「全平後」是写死字串。`main.py:232-238` 启动时立即 create_task，`run()` 先 sleep(30) 再 tick，故 15:54:44 + 30s + 两次 API ≈ 15:55:22 精确吻合。
- **残单来源**：14:57 全平时旧版 `571cc51` 的 `cancel_all_for_symbol` 只撤一般挂单；`989e9a8` 才补上 `cancel_all_orders(..., {"stop": True})` 撤条件单 + `fetch_open_orders` 查 `/fapi/v1/openAlgoOrders`。旧版漏掉的那张 reduce-only 条件单，新版重启后第一次对账查到并撤掉，属修复生效。
- **「收到全平当下就检查挂单」确实已有**：`trigger_router.on_event` 全平四条件（sl_hit/all_tp/close/hedge_exit）立即调 `order_manager.close_all(symbol)`，注释写明「一次性动作、不重试、不事後補做」；`close_all` 无持仓也执行终态撤单。
- **「重连后不处理旧消息」确实没做到（真实缺口）**：`signal_source/telegram_userbot.py:234-242` 的 `events.NewMessage` / `MessageEdited` 无时间过滤；`msg.date` 存进 `RawMessage.ts` 后全 `src/` 从未被读取。程序不主动 `iter_messages`/`catch_up`，但 Telethon 会自动补离线期间的 updates（官方 issue #4021 维护者 Lonami 回复 + `_update_loop` 的 `get_difference`）。唯一防线是 `storage/db.py` 的 `UNIQUE(chat_id, order_id, line_hash)` 幂等，只挡重复、挡不住「离线期间第一次见到的消息」。风险：离线几小时后重连，旧报单会被当新单执行。
- **设计矛盾**：`trigger_router` 注释「不事後補做」与 `watchdog.py` 文件头「程序重啟錯過通知時，殘留掛單仍會被清掉」语义冲突。
- 可选修法（用户未授权，本轮未改）：① `_dispatch` 用 `msg.date` 加时间门槛（只处理晚于进程启动时间或最近 N 分钟）；② watchdog 关闭重启兜底或只清本次进程生命周期内产生的残单。
